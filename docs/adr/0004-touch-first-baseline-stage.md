# 触屏升级为一等输入：基准舞台等比缩放，讲内横屏专用

2026-07-30 定（上 ECS 后第一件事）。本站原本的成文铁律是「只有鼠标、可以用 hover、不碰触屏」
——那是"只在家长那台电脑上跑"时代的正确简化。上了公网 HTTPS 之后课要能带出门，孩子改在
iPhone（Air / 17 Pro）上玩，铁律翻案：**触屏与鼠标同为一等输入**。五条派生决定：

- **几何一处定义：基准舞台。** 两讲的环节几何全是固定 px 的绝对布局（拖拽落点、吸附判定
  全靠 px）。为手机逐环节重排 = 14+ 个环节 × 两套布局，正是共享件那两次「两份必漂移」的
  老路。所以定一个恒定逻辑分辨率的基准舞台，整讲 `transform: scale()` 等比缩放到实际屏幕，
  不足处由讲内背景补边。拖拽只需在 搭台.js 一处补缩放系数（`getBoundingClientRect` 读到的
  是缩放后的视觉坐标，写 `style.left` 用的是舞台坐标）；第2讲射线拾取用 rect 归一化坐标，
  缩放自动抵消，一行不用动。基准尺寸不拍脑袋：从「触靶红线」倒推——越矮的基准在手机上
  缩放系数越大，以最高的环节内容为下限、孩子触靶的物理尺寸为硬验收。
- **讲内横屏专用。** iPhone 竖屏 402pt 宽塞 1280 基准宽，缩放系数掉到 0.31，什么都按不着
  ——竖排不是适配是重设计。竖屏盖转屏拦罩（共享件，图形动画 + 已解锁时语音念一句），
  转过来原地继续（面板本就不销毁，这条白送）。大人页不拦。
- **舞台里不许有视口单位。** 这是「一套布局」这条路上最隐蔽的一处，差点整个方案都被它废掉：
  `vw`/`vh`/`dvh`/`svh` 永远按真实视口算，祖先身上的 transform 完全不影响单位解析。
  于是画在 1280×842 舞台里的 `min(600px, 70vh)`，在手机上算的是那台手机 ~358pt 的七成
  ≈250px —— 周围全按舞台缩放走，就它按窗口走，版面不是等比缩小而是**扭曲**。桌面上
  一点看不出来（窗口本来就 900 上下），所以它能一路活到孩子手上。两讲原本到处是
  `min(…px, …vh)` / `clamp(…px, …vw, …px)`：第3讲七处，第2讲连注入式样式表在内二十余处。
  全部换成舞台像素或对定尺父元素取百分比。舞台外的那几处（html/body 的高、开始遮罩、
  转屏拦罩、纸样打印区 —— 打印要真毫米）正当保留。
  这条**能自动化**，所以做成了红线：`web/shared/test/舞台里没有视口单位.test.js`，
  放行名单必须写理由，写了却没命中的过期条目一样算红。
- **hover 降级为纯装饰。**「这里能点」不许再只靠 hover / 光标说。全站唯一一处光标当唯一
  信号的（第2讲逐面折的可折格子）在粗指针设备（`@media (pointer: coarse)`）上补呼吸提示，
  与「可折(下标)」共用同一个真值。装饰性 hover 包进 `@media (hover: hover)` 防触屏粘滞。
- **触靶下限成文，而且下限是物理的。** 红线是「在最小的那台手机上横过来，孩子要点的东西
  渲染出来不小于 44pt」。**舞台像素数是推出来的，不是定出来的**：

      需要的舞台像素 = 44 ÷ 系数，   系数 = 可视高 ÷ 基准高

  最小机型是 iPhone 17 Pro 横屏（874×402pt，扣掉浏览器工具栏约 358pt 可视），**不是** Air。
  两讲各算各的，算式写在各自样式表的头注释里，数也确实不一样：

  | 讲 | 基准高 | 谁定的 | 系数 | 触靶下限 |
  |---|---|---|---|---|
  | 第3讲 | **842** | 宝藏（内容 668 + 174 让位），一点余量都没有 | ≈0.425 | **104** 舞台像素 |
  | 第2讲 | **740** | 贴水果（705）夹在导航的 640 与「导航图标不缩」的 781 之间 | ≈0.484 | **92** 舞台像素 |

  别把一讲的像素数抄到另一讲去 —— 同一个数字在两边落成的物理大小不一样。共享件更不许挑
  某一讲的系数硬写：麦克风坞和语言开关都写成 `max(设计尺寸, 物理尺寸 ÷ var(--舞台系数))`，
  让 CSS 自己按当前那一讲的系数折算。

  **写这条时先写的是「≥80px」，那是错的**——80 是拿 44pt 除以一个凭空假设的 0.63 系数得来的，
  而 620 的假想基准高被实测推翻（讲的版面本来是照 800 高的桌面窗口排的，压不下去，
  压下去就得改孩子看见的东西）。之后又错了一轮：第3讲一度定在 814、下限记成 100，
  那是**在清掉视口单位之前**量的——`vh` 那时还按窗口算，量出来的内容高本身就是假的
  （见上一条）。清完再量才是 842 / 104。留着这两步是因为下一个人很容易再犯同一步：
  **先清视口单位，再量内容定基准，再由基准推触靶。顺序错了，三个数全是假的。**

  够到下限有两条路，按「邻居是谁」选：
  - **隐形热区**（`热区` / `热区不动位`）外扩量按系数反向补偿，不论缩多小都稳定多出约 20pt。
    所以条件松成 `舞台像素 × 系数 + 20 ≥ 44`，即 `≥ 24 ÷ 系数`（第3讲 57、第2讲 50）。
    用在孤立的控件上。
  - **真放大到下限**：邻居是**另一个答案**时只能走这条。热区往外扩的是看不见的范围，
    两个相邻答案各扩一圈会在中间叠上，孩子按在缝上提交的是隔壁那个答案 ——
    按错导航能退回来，按错答案是判错。方位牌一排、坞上的备选答案一排都属这一类
    （方位牌因此把托盘的间距也拉开了：宁可挪位置，也不让答案互相偷点击）。

  一处成文的例外：**第3讲相邻答案格（冰箱格 / 货架格 / Boss格，96 舞台像素 ≈41pt）就停在 41pt。**
  差的 3pt 换不来什么：格子之间误按的概率由**格距**决定而不是绝对尺寸，96 舞台像素的格子
  远超指尖精度所需；而把它们放大会撑高最高的那个环节 → 抬高基准 → 压低系数 → 又抬高下限，
  是个自己咬自己的圈。

  重来角、家长钮故意小、防孩子误点，是功能不是缺陷，不适用本条。

## Considered options

- 逐环节媒体查询重排（否：每个环节养两套布局，必漂移）。
- 只适配大人页、孩子仍只在电脑上玩（否：公网部署的意义就是课能带出门）。
- 小屏才启用舞台缩放、桌面保持现有流式（否：两条布局路径并存，每个新环节要测两遍）。
- 手机上摄像头换后置（否：环节的情感设计是「镜子里的我举着作品被夸」，后置把孩子本人
  裁掉了；`facingMode: 'user'` 保持原样）。

## Consequences

- 桌面从「流式填满窗口」变为「定比例舞台 + 背景补边」，观感有轻微变化——这是「一条代码
  路径」的价。
- iPhone 上的 Chrome 内核是 WebKit，实际兼容目标是 Safari 引擎；`100vh` 改 `100dvh`、
  `viewport-fit=cover` + 安全区留边、`touch-action` 收口这批坑随本决定一起进代码。
- 以后每个新环节天生手机兼容：画在基准舞台上、触靶够到本讲算出来的那个下限、hover 只做
  装饰，没有第二套规则要记。
